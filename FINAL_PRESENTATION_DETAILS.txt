4. WHY CUSTOM C++ AGENT vs. AWS CLOUDWATCH AGENT (From Proposal)
================================================================================
1. Granular Control & Adaptive Ingestion:
   - CloudWatch agent streams generic metrics on static intervals.
   - Our C++ agent uses differential kernel ticks from /proc/stat and /proc/meminfo (<0.5% CPU overhead), and dynamically attaches top 3 offending process diagnostics ONLY during sustained spikes (>=85% CPU for 2 cycles).

2. Active Remote Incident Orchestration:
   - CloudWatch is passive monitoring only.
   - Our system provides a closed-loop remediation channel allowing operators to inspect and terminate runaway processes directly from a mobile dashboard.

3. Engineering Depth:
   - Complete mastery of systems programming (C++17), serverless cloud ingestion (API Gateway + Lambda), relational JSONB indexing (PostgreSQL), and modern mobile UI (Flutter).

5. MULTI-LAYER SECURITY & KILL GUARDRAILS
================================================================================
Layer 1: OS Protected Process Blocklist
  - Hardcoded server-side protection preventing termination of:
    systemd, init, sshd, dbus, dbus-daemon, networkmanager, dockerd, containerd,
    cron, rsyslogd, telemetry_agent, [kernel]
  - Returns HTTP 403 Forbidden if attempted (Execution Rejected: Process <name> is protected).

Layer 2: 2-Minute Diagnostic Telemetry Verification
  - Lambda verifies against RDS that the target PID was actively observed in
    high-CPU diagnostics (>=85%) on that specific server_id in the last 120s.
  - Returns HTTP 403 Forbidden if unverified or PID guessing is attempted.

Layer 3: Cryptographic 8-Character SHA-256 Confirmation Token
  - Frontend generates sha256(server_id:pid:cmd)[:8] (e.g. 'a3f9e2b1').
  - The operator must type the exact 8-character confirmation code (or executable name)
    to unlock the Terminate button.

Layer 4: Immutable Pre- & Post-Execution Audit Trail
  - Inserts pre-execution record in kill_commands table with 'authorized' status.
  - Updates the same row to 'dispatched' (with SSM Command ID) or 'failed_dispatch' (with error message).

7. END-TO-END PROJECT WORKFLOW (DETAILED STEP-BY-STEP)
================================================================================

The system operates across two core real-time workflows:

--------------------------------------------------------------------------------
WORKFLOW A: Continuous Telemetry Ingestion & Diagnostic Spike Burst
--------------------------------------------------------------------------------
Step 1: Kernel Metrics Capture (Every 3 seconds on EC2)
  - The C++ telemetry agent reads raw Linux kernel counters from /proc/stat
    (CPU jiffies: user, nice, system, idle, iowait) and /proc/meminfo.
  - Computes exact differential CPU% using: (TotalDiff - IdleDiff) / TotalDiff * 100.

Step 2: Adaptive Spike Detection & Dynamic Process Attachment
  - If CPU usage is normal (<85%): Agent builds a lightweight JSON payload (136 bytes)
    with only aggregate metrics (server_id, cpu_percent, ram_percent, timestamp).
  - If CPU exceeds 85% for >= 2 consecutive cycles (10s sustained spike):
    Agent scans /proc/[pid]/stat, calculates per-process CPU shares, extracts command
    lines from /proc/[pid]/cmdline, and dynamically attaches top_processes to the payload.

Step 3: Secure Cloud Ingestion (API Gateway -> Lambda)
  - Agent POSTs JSON payload to API Gateway (/IngestMetrics) with 'x-api-key' header.
  - API Gateway validates CORS and routes the event to AWS Lambda (Python 3.12).
  - Lambda verifies the API key (fail-closed model) and connects to PostgreSQL.

Step 4: Relational Persistence & JSONB Indexing (Amazon RDS)
  - Lambda executes an INSERT into 'telemetry_logs' storing cpu_percent, ram_percent,
    and top_processes in a native JSONB column.
  - Returns HTTP 200 OK: {"message": "Metric ingested successfully"}.

Step 5: Real-Time Visualization (Flutter Operator Portal)
  - Flutter app polls GET /GetMetrics every 3 seconds for the selected server.
  - Renders live dual-axis fl_chart line graphs (Cyan = CPU, Orange = RAM).
  - If latest record contains top_processes, Flutter automatically triggers the
    prominent Red Spike Alert Banner displaying the rogue process name and PID.

--------------------------------------------------------------------------------
WORKFLOW B: Guardrailed Remote Incident Remediation (Zero-SSH)
--------------------------------------------------------------------------------
Step 1: Human-in-the-Loop Guardrail Trigger
  - Operator clicks 'Kill Process' on the red alert banner in Flutter.
  - Flutter generates an 8-character cryptographic token: sha256(server_id:pid:cmd)[:8].
  - Safety modal prompts the operator to type the 8-char code (or process name)
    to unlock the 'Terminate' button, preventing accidental clicks.

Step 2: Command Dispatch to AWS Backend
  - Flutter sends POST /ExecuteCommand with:
    {server_id, pid, process_name, force_kill (true/false)} and x-api-key header.

Step 3: Multi-Layer Security Verification in Lambda
  - Check 1 (Blocklist): Verifies process is not protected (rejects systemd, sshd, dbus, cron).
  - Check 2 (2-Min Spike Audit): Queries PostgreSQL to verify this exact PID was
    actually reported in a high-CPU spike on this server in the last 120 seconds.
  - Check 3 (Pre-Execution Audit): Inserts a record in 'kill_commands' with status 'authorized'.

Step 4: AWS Systems Manager (SSM) Remote Execution
  - Lambda invokes boto3.client('ssm').send_command(DocumentName='AWS-RunShellScript')
    targeting the specific EC2 Instance ID.
  - Command: 'kill -15 <pid>' (graceful SIGTERM) or 'kill -9 <pid>' (force SIGKILL).
  - Amazon SSM Agent on EC2 receives the payload and terminates the rogue Linux process.

Step 5: Audit Finalization & UI Confirmation
  - Lambda receives the SSM Command ID, updates the 'kill_commands' audit row status
    to 'dispatched' with the Command ID.
  - Returns HTTP 200 OK with confirmation message to Flutter.
  - Flutter displays success SnackBar, the server CPU drops back to 0%, and the
    alert banner automatically clears!
